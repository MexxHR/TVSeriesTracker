## 3. Persistence choice and rationale

Separate Preferences DataStore file **monitoring_intents_v1**, application-context singleton. Existing settings DataStore file/keys and Room schema are untouched. DataStore.edit serializes atomic map/receipt changes across ViewModel and worker instances. A DataStore<Preferences> constructor permits actual library/file tests without Android Context.

Each ID has a bounded versioned line record under an intent key; this is not an uncontrolled JSON blob. Decoder validates version/count/ID/key/phase/receipt/timing/count bounds. Key carries validated ID and encoded series identity so a malformed record can recover as PREPARED rather than falsely complete. Whole unreadable protobuf/storage IO is fail-closed, not silently reset; fixing arbitrary disk corruption is not claimed. Maximum1000 intent rows; storage errors are surfaced/retained rather than interpreted as completion.

## 4. Durable intent model / invariants

Record: tmdbId, seriesId, localKey, phase, nullable receipt, nextAt and legacyAttempts0–3. Five small phases:

| Phase | Meaning / invariant |
| --- | --- |
| PREPARED | Durable write-ahead Add intent; never submitted until watchlist commit is known |
| SUBMIT | Submission/repair required; no receipt |
| RECEIPT | Accepted exact receipt, status unresolved |
| CANONICAL | Exact COMPLETE already observed/persisted; only canonical fetch remains |
| LEGACY | Accepted without receipt; separate limited compatibility behavior |

Receipt is present only in RECEIPT/CANONICAL. localKey is a client-only random intent identity, never sent to backend; it rejects stale callbacks/clears after remove/re-add. It is not a server generation, lease or workflow attempt. Conditional updates compare the full expected local record and return whether they won, preventing equal-clock concurrent transport reservations from both POSTing.

Two small global timing records are necessary: next status window and up to three recent submission timestamps. They bound restart/resume storms without storing workflow history or replicating server attempts.

## 5. Add ordering and process-death gap

To close the gap between two independent stores without Room migration, Add uses **write-ahead PREPARED -> existing watchlist save -> SUBMIT activation -> WorkManager ensure**. This deliberately strengthens the conceptual watchlist-first ordering: a committed watchlist insert cannot be left without an already durable marker if the process dies before activation. PREPARED cannot submit by itself.

Startup/resume under the same local Add mutex observes followed series: committed PREPARED becomes SUBMIT; uncommitted/unfollowed PREPARED is removed. Remove and Add share that mutex so repair cannot prune a concurrently committing Add. Existing repository metadata enrichment behavior is preserved; monitoring network submission never precedes or blocks the watchlist insert.

Enqueue/query failure does not roll back Add. If preparation storage itself fails, the existing watchlist save is still attempted and the storage error is surfaced through existing error handling; no false monitoring-success claim is made. There is no way to promise durable intent on an unwritable disk, and no hidden in-memory fallback.

## 6. WorkManager role

WorkManager is transport only. Retains unique official-monitoring-ID, KEEP, CONNECTED and exponential30-second backoff/bounded retries. ensure() queries existing unique work asynchronously on IO with bounded waits: ENQUEUED/RUNNING/BLOCKED is retained; empty/SUCCEEDED/FAILED/CANCELLED permits enqueue. Operation/query errors propagate to durable repair handling.

Worker reads the durable row before submission, skips non-SUBMIT/not-due work, persists cooldown before POST, and saves accepted receipt/legacy state before returning success. Missing row after remove is a transport no-op. Terminal WorkManager work cannot erase unresolved intent. Missing/failed/query-failed work is repaired on active coordinator/startup/resume. Actual Android engine execution is not exercised locally; predicate, request properties, source adapter compile and fake-boundary repair tests are exercised.

## 7. Submission contract

ID-only POST /v1/series-requests, HTTPS,8-second timeouts, redirects disabled, bounded8KiB response.202 requires accepted=true, matching positive integer tmdbId and queued/already_queued; optional receipt must be lowercase hex64 if present. Unknown fields/duplicate keys/trailing JSON/malformed types are rejected. No response fields become factual data. Invalid transport configuration is constructed lazily so it cannot crash local app dependency construction.

## 8. Legacy compatibility

Absent requestReceipt is accepted, not fabricated. Persist LEGACY with no status call. Three compatibility canonical refresh attempts retain nominal30/90/210 timing and persist their budget across process/lifecycle restarts. Exhaustion leaves the unresolved LEGACY marker; it never claims batch completion.

Exhausted legacy rows stop the timer. On a later startup/resume at least24h after that bounded sequence, one rate-bounded submission reprobe is permitted. This is an opportunistic compatibility/cutover bridge, not continuous legacy polling; if backend now returns a receipt, ordinary batch reconciliation starts. No production mode change is performed by Android. Legacy behavior is not claimed to meet the batch completion guarantee or live KPI.

## 9. Receipt persistence / replacement

Receipt save is atomic with RECEIPT phase/timing. Once saved, status checks replace progress POSTs. Duplicate Add coalesces an existing obligation and does not churn its receipt/cooldown. If POST reached server but process died before receipt persistence, the reserved durable SUBMIT remains; after bounded cooldown a new POST may legitimately obtain a new server receipt. That unavoidable at-least-once uncertainty does not create false completion.

Local expected-record matching prevents an old response from restoring a removed/re-added intent. Tests explicitly force equal-clock concurrent submission reservations and prove one POST, and force removal/re-add while an old response is in flight.

## 10. Exact status API

POST /v1/series-requests/status sends exact tmdbId/requestReceipt in body, never URL. Actual Phase1 response schema is tmdbId/state. Matching ID and exact pending/complete/unknown are required. Wrong ID, extra/duplicate fields, invalid JSON, timeout and transport errors cannot become UNKNOWN or COMPLETE. They retain the current receipt with bounded delay.

## 11. UNKNOWN recovery

Only authoritative HTTP200 unknown transitions RECEIPT -> SUBMIT without receipt, with a20-minute submission recovery cooldown. It never clears intent. Later WorkManager transport obtains/persists a fresh receipt. A429/5xx/malformed/error response cannot trigger that transition. Local/global durable submission limits prevent tight POST/status loops or restart receipt churn.

## 12. COMPLETE handling

Exact COMPLETE atomically transitions to CANONICAL and schedules a bounded30-second visibility grace. After restart, CANONICAL needs no new status check and no processing resubmission. If persistence fails/cancellation occurs before transition commit, existing receipt state remains for another authoritative status check. COMPLETE is never mapped to renewed/canceled/no-fact UI status.

## 13. Canonical reconciliation

Coordinator calls the existing OfficialDataRepository.refresh("durable-monitoring"). No second canonical fetch/parser/cache path. Its HTTPS/JSON/Instant/mutex/Room/SAME/OLDER behavior is unchanged. One canonical refresh covers all due CANONICAL rows and any legacy compatibility rows. Successful return may be NEWER or a validated no-replacement fetch; the Boolean indicates cache update, not fetch success. Exceptions retain canonical-needed state and defer retry.

## 14. Exact completion criterion

For batch mode: **exact receipt COMPLETE persisted + subsequent successful canonical reconciliation + expected local record still current -> clear**. Nothing else clears that obligation. If removal/re-add occurs during canonical fetch, the expected-record comparison cannot remove the new intent. A process death after fetch but before clear simply replays a fetch after restart.

**ANDROID_COMPLETION_CRITERION_RESOLVED** at deterministic code level. Canonical cache alone, global generatedAt advance,202, worker result and exhausted timer cannot satisfy this predicate. Backend COMPLETE remains processing-pass completion, not proof of a new factual record or a strongest possible CDN content identity.

## 15. NO_CHANGE / no-fact / existing fact

Tests connect the actual coordinator to actual OfficialDataRepository/OfficialDataParser with injected remote/store, covering SAME and NEWER, existing fact and no fact. SAME resolves without requiring generatedAt change. Clean no-fact resolves the immediate pass and leaves existing unknown/no-verified-data UI. An existing cached fact does not clear a receipt before COMPLETE. OLDER never overwrites newer cache; a successful validated older fetch still preserves that newer cache.

The30-second grace plus shared canonical refresh is a bounded practical visibility policy, not proof that every cache has the latest publication. No expected-content hash/backend extension or generatedAt completion heuristic added. Live CDN timing remains Phase3 measurement.

## 16. Foreground / resume / startup coordinator

SeriesViewModel wires existing root lifecycle callback to one MonitoringReconciler. Startup/resume repairs PREPARED against followed rows and starts one loop. Durable DataStore Flow only wakes it; it is not a process-local correctness event. Mutations do not cancel in-flight cycle work. Coordinator checks/repairs due SUBMIT, checks due receipts, and coalesces canonical work. Conditional updates protect racing removal/re-add.

## 17. Cadence / rate budget

Status admission is globally persisted: at most two checks per120-second window, fair oldest nextAt then ID. Nominal60/hour, at most62 in an inclusive rolling-hour boundary, below120/client/hour with headroom for metadata/search. <=3 receipts share slots; backlog does not create one timer per ID. Global Retry-After defers all receipt checks, including the remaining candidate in the same cycle.

Submission allows at most three reserved POST opportunities in a20-minute local window, with per-intent20-minute recovery reservation and authoritative Retry-After. This is nominal9/hour; server quota remains authoritative at inclusive boundaries/new Adds.429 defers rather than loops. Interrupted actions may consume a local opportunity without sending, intentionally conservative. WorkManager state inspection has a30-second minimum local repair timer while due work exists; it is not a status HTTP poll. Empty/exhausted-legacy state waits for changes without active timer.

## 18. Background behavior

Lifecycle stop cancels coordinator/observer and active coroutine work, never deletes durable intent. Resume reconstructs from DataStore. WorkManager may continue connected unsent transport; no status foreground service, periodic status worker, push notifications or permanent background polling. Foreground timing is not a background-display SLA.

## 19. Process-death race evidence

| Boundary | Restart behavior |
| --- | --- |
| Prepared before Room commit | Drop if not followed; activate if committed |
| Intent committed before enqueue | SUBMIT repaired |

| Old response/clear after remove/re-add | Local key/expected-record mismatch rejects it |

## 20. Remove / re-add

Successful unfollow removes matching local obligation under Add/remove mutex. Startup pruning also repairs a crash between Room remove and intent remove. No backend cancellation. Re-add creates a fresh local key after removal; stale HTTP results/canonical clears cannot resurrect or clear it. Old unique WorkManager work may harmlessly finish; later repair handles its terminal state. Server processing may legitimately finish independently.

## 21. Offline

Local watchlist/pending preparation uses existing storage, not monitoring HTTP. WorkManager waits on CONNECTED and durable deadlines survive restart. Status/network failures keep receipts. Canonical failure after COMPLETE keeps CANONICAL, without re-POST. Returning online/foreground repairs due work. Existing Room factual cache remains usable; monitoring state never substitutes for it.
