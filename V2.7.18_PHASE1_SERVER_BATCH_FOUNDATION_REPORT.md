## 3. Backend schema before / after

Existing tables retained: requests(tmdb_id,at), rate_events(ip_hash,at), tmdb_rate_events(ip_hash,at), with their existing indexes. Added pending_requests with exactly five approved columns:

```text
tmdb_id INTEGER PRIMARY KEY
request_receipt TEXT NOT NULL UNIQUE
requested_at REAL NOT NULL
next_eligible_at REAL NOT NULL
completed_at REAL NULL
```

Added selection index only, no additional persisted column. NULL completed_at means pending. Non-NULL means that exact immediate processing receipt completed, not that verified facts necessarily exist. No provider/workflow/run/attempt/lease fields.

## 4. Migration strategy

CREATE TABLE/INDEX IF NOT EXISTS is additive and repeatable on new or legacy DBs. Existing request/rate rows are not reset or interpreted as success. Schema initialization does not import historical acknowledgements into active work.

RequestStore.import_legacy_requests() is a separate explicit, transactional staged helper for cutover. It imports missing IDs in the still-current24h acknowledgement horizon as pending, subject to capacity, with fresh receipts and conservative eligibility. Existing pending/completed rows are not overwritten. Old legacy rows, including expired ones, remain in their old table. Repeated import preserves quotas and existing receipts; it is not periodic housekeeping. Known older unfinished work must be separately inspected/reconciled rather than assumed complete. No real database migration was executed.

## 5. Public POST compatibility

POST /v1/series-requests still accepts exactly {tmdbId}, positive integer within existing bounds, no bool/extra fields/duplicate keys, existing bounded body/content checks and client/global admission quotas. Legacy mode still returns the original accepted/tmdbId/state fields and performs the existing dispatcher path. Batch mode adds optional requestReceipt; existing Android classifier continues to understand queued/already_queued. No client request field added.

## 6. Batch-mode admission semantics

SERIES_REQUEST_MODE defaults to legacy. Only exact batch enables new semantics. Batch startup does not construct GitHubDispatcher or require a PAT/repository setting; it requires the dedicated batch secret. No GitHub API call is needed to admit work.

Under BEGIN IMMEDIATE: new/completed ID becomes pending with new request time/eligibility; already pending ID gets a new receipt while preserving original requested_at and next_eligible_at. All return paths leave the context manager before HTTP202, so commit errors cannot produce false success. DB failures return503. No dual dispatch in batch mode; legacy dispatcher remains available for transition/rollback.

## 7. Pending capacity

Hard capacity1000 unfinished rows. Completed retained receipts do not count. A new obligation at capacity returns503 queue_full with Retry-After600; no pending work is evicted. Refreshing an existing pending member does not consume another slot or reset its retry deferral. Boundary and completed-row capacity tests pass.

## 8. Receipt semantics

secrets.token_hex(32) creates a256-bit opaque receipt for every accepted batch POST, including equal-clock duplicates. A UNIQUE constraint/collision check protects current rows; cryptographic non-reuse is probabilistic at negligible collision risk, without retaining permanent historical tokens. Receipt is request correlation, not an attempt ID or publication credential. It is never printed in normal consumer logs.

Completed receipts are retained seven days and purged during normal endpoint activity after that horizon. Pending rows have no TTL. Once expired, old status is unknown and old ACK cannot complete a new obligation. No cleanup daemon.

## 9. Snapshot API

POST /internal/series-batch/snapshot requires batch mode, HTTPS, dedicated Bearer auth and strict {} request. Server-fixed maximum3 due unfinished rows, ordered next_eligible_at/requested_at/tmdb_id. Reply: {items:[{tmdbId,requestReceipt,ackProof}]}.

Selection runs under BEGIN IMMEDIATE and advances selected next_eligible_at by600seconds. It does not remove membership, assign running status/owner, reserve exclusive execution or require release. Crash after selection leaves pending work. Concurrent snapshot tests show bounded selection and no simultaneous repeated due selection.

## 10. ACK proof

Domain-separated SHA-256 HMAC covers purpose/version, ID and exact receipt. No batch/run history is persisted. Auth and proof comparison use hmac.compare_digest. Wrong ID/receipt/proof and unselected tuples without a valid issued proof are rejected before completion writes. A trusted secret holder is trusted to execute workflow code; HMAC is not independent proof of provider processing or Git publication. It authorizes pending completion only.

## 11. Conditional completion API

POST /internal/series-batch/complete requires the same auth/HTTPS and a strict items list of1–3 exact ID/receipt/proof tuples. Every proof is validated before any item mutation in one SQLite transaction. Matching pending -> complete; same completed receipt -> already_complete; missing/different receipt -> stale, no newer row mutation. Response items contain ID/state only. Mixed valid/invalid proof lists fail atomically. Duplicate ACK and restart between snapshot/ACK are tested.

## 12. Receipt status API

POST /v1/series-requests/status requires one bounded exact ID/receipt pair, returns tmdbId and pending/complete/unknown with no-store. Incorrect, expired, absent and superseded receipts all return unknown. This deliberately avoids revealing another request's existence through unknown-vs-superseded differences. It cannot list pending IDs or reveal other receipts/provider facts/workflow state.

Status uses existing metadata quotas120/client/hour and3000/global, avoiding consumption of the separate10/client/hour and200/global admission quota. No new rate table/column and no quota reset. Phase2 must respect429/Retry-After and aggregate reconciliation work.

## 13. New-request-before-old-ACK proof

Production-backend tests exercise both linearizations:

```text
POST123 -> R1; snapshot R1/proof1
POST123 -> R2 (same row, new receipt)
ACK R1 -> stale; R2 pending
later snapshot/ACK R2 -> complete

ACK R1 first -> complete
then POST123 -> new R2 pending
```

Receipt matching is atomic entirely in SQLite, including equal-clock requests. No GitHub state is read by the backend and no old publisher is revoked.

## 14. Batch orchestrator

controlled_batch.py fetches the bounded snapshot only inside the admitted workflow, processes IDs sequentially and ACKs eligible results. GitBoundary requires clean main and exact fetched origin main; both monitored and canonical pushes retain the existing normal-push conflict behavior. Every next ID starts at a clean validated boundary. No multi-ID dirty accumulation, per-ID dispatch fan-out, matrix, silent reset/rebase or force push.

Existing stage snapshot/verification, production preflight/verification and publishers are reused. Unexpected/global unsafe failures stop the run with sanitized counts; no generic continue-on-error. API ACK failures are truthful failures, not assumed success. Empty snapshot processes no provider. CLI default is local readiness validation only, with zero API/provider calls or publication; --execute additionally requires the exact readiness gate.

## 15. Per-ID outcome -> ACK mapping

| Outcome | ACK rule |
| --- | --- |
| Guarded canonical change with successful push and clean current head | ACK |
| Independently validated canonical NO_CHANGE | ACK after required monitored publication |
| Clean NO_VERIFIED_FACTS / NOT_PARSER_ELIGIBLE / DISCOVERY_INSUFFICIENT | ACK only after allowed staging boundary/publication and no discovery warning/transport failure |
| Clean unsupported-provider result | ACK after permitted guarded staging pass |
| VERIFIED_FACTS staging without completed promotion | No ACK |
| Promotion disabled/incomplete | No ACK |
| Provider/metadata unavailable or discovery warning in an otherwise no-evidence pass | No ACK; retain |
| ALREADY_TRUSTED through monitored route | Fatal wrong-route result; never ACK |
| Regression/validation/global/unknown exception, push failure/uncertainty | No ACK; stop unsafe unit/run |

Typed Outcome/Result mapping is not based on exit status alone. Generic discovery wrapping preserves warnings for ACK decisions without changing provider adapters. An unavailable unchanged protected boundary is validated as a no-write retry, including metadata failure/preserved monitored evidence; it is not interpreted as a terminal no-fact pass.

## 17. Poison fairness

Snapshot scheduling touch persists even if a run fails before processing all selected IDs. Older unselected eligibility sorts before deferred selections on the next run. Repeated POST does not reset this deferral. Backend tests and existing architecture diagnostics cover due ordering/crash/rotation. Understood nonfatal retry outcomes can continue only from a clean validated boundary; unsafe/global exceptions abort. Global corrupted inputs require review and are never bypassed for fairness.

No retry counter, dead-letter queue, claim or exponential server attempt state. Current fixed600-second selection deferral is the minimal admitted retry spacing. Persistent failures remain visible in sanitized run failures/backlog and may require operator action; indefinite outage is not claimed automatically repaired.
