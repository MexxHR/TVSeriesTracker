# V2.7.18 Backend Recovery Contract

**V2.7.18 BACKEND RECOVERY CONTRACT STOPPED — LEASE_EXPIRY_SAFETY_BLOCKER**

Analysis: 2026-10-16, Europe/Zagreb. This is a feasibility-gated continuation, not a completed implementation. Runtime/backend/workflow/Android files were not changed. No version bump, deployment, live request, dispatch, provider fetch, promotion, APK or release ZIP.

## 1. Executive summary

The approved terminal-callback design can release a known terminal attempt promptly. It cannot safely distinguish a lost attempt from a healthy queued/running attempt when the callback has not arrived. Current workflow configuration supplies no minutes-level upper bound on dispatch-to-terminal time. Sections 12/13/23/38 require stopping at this safety gate rather than choosing an unsupported TTL. No runtime implementation was started.

Source of truth: V2.7.17_E2E_STABILITY_FORENSICS.md and V2.7.18_E2E_RELIABILITY_REPORT.md. The continuation prompt explicitly authorizes backend work but separately requires this STOP if safe expiry cannot be designed within scope. Android completion uncertainty is not the reason for stopping.

## 8. Active duplicate behavior

Existing BEGIN IMMEDIATE submission remains unchanged and suppresses same-ID duplicates for 24h. Proposed shorter expiry would introduce recovery dispatches without evidence that an old attempt ended. Keeping that suppression indefinitely would instead fail lost-callback recovery. Neither alternative satisfies the complete new contract.

## 9. Terminal callback behavior

No endpoint or workflow callback installed. Candidate future path must authenticate and correlate ID/attempt, reject malformed requests and stale attempts, and be idempotent. A terminal job would need to depend on both monitored_update and promote, account for skipped promotion/failing earlier jobs, and preserve truthful failure results. A happy-path-only step is inadequate. These are requirements, not tested implementation claims.

## 10. Lost callback / lease expiry

After dispatch acknowledgement and before callback, persisted ID/attempt/start/state/current time can be identical in two worlds: A disappeared; A is still healthy in the shared queue or executing. A timer has the same inputs in both worlds. Redispatch recovers the first but duplicates the second. Suppression protects the second but does not recover the first. Terminal-only signaling supplies no additional observation at this boundary.

## 11. Lease duration and evidence

**Chosen duration: NONE — blocked.** Illustrative 240/600/1800/3600 second values in the diagnostic are counterexamples, not proposed defaults or measured runtimes.

Local workflow evidence:

- Two sequential jobs: monitored_update and conditional promote. Both lack explicit timeout-minutes. Regression discovery, checkout/setup, git fetch/push, processing, validation and promotion occur inside this serialized workflow.

No runner timing history was fetched and no typical runtime is invented. Even a measured usual runtime would not establish a queue-aware upper bound. No externally assumed GitHub default timeout is needed for this conclusion. A job timeout, even if later authorized, would not alone bound time before that job starts. Increasing TTL to hours/days would not establish the requested reasonable-minutes recovery.

## 12. Expiry race analysis

Deterministic synthetic permitted schedule: TTL=600 seconds; A acknowledged at 0 and still running until 720; request at 601 expires A and queues B. Shared writer serialization keeps one writer running, but two dispatches/attempts exist and B can execute after A. Another case holds the group with a different writer until 720: A expires before its first job even starts, and retry queues B.

These models prove a contract counterexample, not an observed production duration and not an implemented lease test. Exact-head checks, canonical validation and promotion idempotency remain valuable data safety controls; none revokes a stale dispatch before processing or supplies backend liveness. A synthetic timer policy cannot claim the healthy-at-expiry case safe solely because repository writes are serialized.

The current scope permits only attempt input/callback/retry/terminal paths in YAML. It does not authorize queue restructuring, workflow admission fencing or execution deadline changes. No such workaround was introduced. A heartbeat beginning inside the job would itself miss pre-start queue waiting, so **HEARTBEAT_REQUIRED is not established as a sufficient remedy**.

## 24. Recommendation / smallest next design decision

Backend recovery primitive is **NOT READY**; do not resume Android durable pending as if it were fixed. Before runtime work, review a queue-aware stale-attempt admission/fencing contract (old queued work must be prevented from processing after replacement) or an explicitly bounded dispatch-to-terminal execution/queue contract compatible with the minutes KPI. Either requires scope beyond terminal callbacks alone and its own failure/security proof. Liveness polling or heartbeat is not silently substituted; in-job heartbeat alone does not solve queued attempts.
