# V2.7.18 — Recovery Fencing Feasibility

**V2.7.18 RECOVERY FENCING — FENCING_NOT_FEASIBLE**

Recommendation: **NO_GO_SIMPLIFY_ARCHITECTURE**.

Date: 2026-10-16, Europe/Zagreb. Read-only architecture analysis with added diagnostic models/report only. No fix, runtime change, live request, workflow dispatch, provider fetch, deployment, promotion, APK or release ZIP. Baseline remains **48 / 2.7.16.1 / Room3 / com.example.tvseriestracker**.

## 1. Executive verdict

A backend-owned current-attempt map can reject work that is already stale when checked. It cannot revoke permission between that check and a separate GitHub push. The current Git receiver validates repository history/credentials, not the backend's current attempt. Shared GitHub writer serialization does not serialize backend generation changes. A permitted schedule therefore publishes A after B becomes current, even with a last-moment authenticated check and exact-head validation.

The verdict concerns the requested strict property and current architecture: obsolete A must not produce relevant mutations after backend supersession. It does not claim every stale result is factually wrong or that every possible fencing architecture is impossible. Closing this gap requires mutation authority and generation changes to share an enforceable boundary, or coordinated publish ownership with crash/uncertain-push recovery. That is beyond a small current-check contract. No positive verdict is forced by accepting eventual repair or a small race window.

Sources of truth inspected: V2.7.17_E2E_STABILITY_FORENSICS.md, V2.7.18_E2E_RELIABILITY_REPORT.md and V2.7.18_BACKEND_RECOVERY_CONTRACT_REPORT.md, plus current workflow and directly invoked shared processing/guard scripts. No live timing/history was used.

## 3. Persistent mutation boundaries and side-effect classification

| Operation | Class | Consequence / fence relevance |
| --- | --- | --- |
| Validate ID, regression gates, parse existing data, git fetch/checkout reads | A: read-only relative to production | Checkout/fetch also change runner-local files; no shared publication |
| Provider/TMDB HTTP GET computation | A with external resource cost | No repository mutation; stale requests can consume provider quota/logs, so not literally zero side effect |
| Snapshots, tee result JSON, staged temp files | B: runner-local mutation | Discardable; RUNNER_TEMP is not a shared repository |
| monitored.publish: monitored_series.json and monitored_changes.jsonl | B in this GitHub workflow checkout | Durable on runner filesystem but not externally published until push; later steps can consume it |
| promotion.promote -> update.publish: official_series_data.json and changes.jsonl | B in runner checkout; intended canonical candidate | Local compute/write is not remote canonical publication |
| git add/config/commit | B | Local object/index/config mutation; becomes shared when pushed |
| Monitored git push | C: persistent/shared | Registry AND monitored audit become observable; later workflows/manual promotion can consume them |
| Production git push | D: canonical production mutation, also C | Canonical JSON AND production audit become observable to Android/other consumers |
| sources.json | Input only here | Guards prohibit changing it; neither request push may include it |
| GITHUB_OUTPUT / job outputs / step summary | C within Actions run metadata | Can authorize/route subsequent promote job; not canonical facts or generation authority |
| Workflow artifacts | None uploaded by this workflow | Temporary result files are not upload-artifact outputs |
| Proposed backend generation update | C | Must persist atomically; not protected by GitHub group |

Compute and remote persistence are sufficiently separated to centralize checks around both pushes; no provider-specific fence is necessary for that separation. This is useful but insufficient for atomic publication. A stale monitored push matters even if promotion later skips: the shared row/audit is already observable and another authorized workflow may consume it. Ordinary diagnostics/summary output is not a verified fact and must never be promoted to current-attempt proof.

## 4. Proposed minimal generation model — assessment only

Candidate map: tmdbId -> currentAttemptId with persisted acceptance time and bounded recovery accounting. SQLite transactions can atomically supersede A with B and serialize concurrent retries. No table/endpoint/input was created.

Opaque random ID is enough for equality-based stale/replay rejection; monotonically increasing generation is also enough if persisted, never reused, and authenticated separately. A number is not a secret. A random ID used only for correlation is not a credential either. Both are unnecessary for a simple equality check. Restart must preserve current identity; restoring an older DB would require operational precautions against identity reuse/rollback.

Monotonic ordering would become useful if the mutation recipient enforced ordered fencing tokens, but current Git push does not inspect such a token. Merely adding an attempt ID to a commit message does not cause enforcement. Neither choice closes TOCTOU.

## 5. Generation owner

Backend can own a small current-attempt map without tracking run/job liveness. It is authoritative about supersession, not authoritative at GitHub's ref-update boundary. Backend ownership alone is sufficient for current-check/callback decisions; insufficient for preventing a separately credentialed workflow from pushing after supersession.

## 6. Queued stale-attempt analysis

A queued; B becomes current; A starts: an authenticated fail-closed early check can reject A before provider work. This case is SAFE ONLY IF the check sees authoritative persisted state, no cached positive admission is reused, and stale paths cannot reach pushes or falsely authorize promote. Queue delay no longer needs a runtime estimate for this particular case. If A is checked before B exists, subsequent cases apply.

## 7. Running stale-attempt analysis

A passes early check and computes; B becomes current before final check: fail-closed final check can discard local results and prevent publication. Provider calls already made cannot be undone and may contribute rate-limit pressure; they need bounded budgets. This case is SAFE ONLY IF supersession precedes the final check and downstream jobs also check independently. A running after a positive final check remains unsafe.

## 8. Critical TOCTOU analysis

Deterministic schedule, with all data/gates otherwise valid:

```text
GitHub main = H0. A holds official-data-writes; B is not executing.
A computes a valid requested-ID change.
A fetches origin main and validates exact expected head H0.
A asks backend: current(A)? -> authenticated YES.
Backend atomically changes current(A) -> current(B); dispatch B is queued.
A creates its local commit if not already created.
A pushes a fast-forward commit based on H0 -> GitHub accepts.
At the remote mutation instant, backend current is B, publisher is stale A.
```

Moving the check after local commit, into the same shell command, or directly before push only shortens the window. Scheduling/network pauses can occur after the response. Even a stronger hypothetical remote exact-expected-head CAS accepts: the backend change did not change H0. Shared writer serialization makes it particularly plausible that B cannot advance main to cause rejection.

Signed short-lived admission/capability tokens prove an earlier grant, not continued currentness. More checks or a check after push cannot retroactively prevent publication. Idempotency only prevents a true factual no-op; choose a valid factual change and the counterexample remains.

## 9. Monitored-write fence

Earliest optimization: before expensive work. Latest useful observation: immediately before monitored push, after all local processing/validation. Checking before monitored.publish is earlier and has a larger window; it is not a remote safety boundary. The push must be covered by enforcement atomic with supersession to satisfy the strict property. Current GitHub ref update has no backend-generation predicate. Monitored stale mutation is therefore not reliably fenced by a small check endpoint.

## 10. Promotion fence

A may publish monitored data while current and become stale before promote starts. A new promotion-stage check is necessary; monitored_state=VERIFIED_FACTS and staged_head prove evidence/repository boundary, not current generation. Yet that new check has the same check-to-production-push race. Both monitored and canonical publication need protection; fencing only canonical leaves stale staging/audit observable. NO_CHANGE does not mutate production and remains safe as a no-op, but cannot justify allowing the changed-result case.

## 11. Multi-job identity

An immutable workflow input could propagate the same backend-issued attempt through both jobs, with strict format/ID checks and explicit environment passing. Outputs/needs are an adequate carrier; fresh checkout should not infer generation from files or current HEAD. Current outputs do not contain attempt identity. Conditional skipped/failed jobs must not leave a positive fence result reusable as later authorization. Stale callbacks need exact identity match. These are small plumbing requirements; they solve identity confusion, not atomicity at either push.

## 12. Shared writer interaction / other workflows

update-official-data.yml serializes its daily/manual update, tests, optional local publish and conditional canonical/audit commit/push. process-discovered-series.yml serializes its read-only preview or monitored-only local processing/commit/push. promote-monitored-series.yml serializes manual guarded promotion and canonical/audit commit/push. preview-monitored-promotion.yml holds the group despite being read-only and verifies no checkout changes.

None uses backend generations; none needs a fabricated request attempt merely to retain current cross-workflow serialization. Request-specific checks could stay local to process-series-request without changing those writers' semantic rules. However, the shared queue does not lock backend currentAttempt updates. It protects repository write ordering, not the strict relationship between supersession and publication. Other workflows may legitimately consume previously published monitored data, making late monitored publication relevant beyond A's own promote job.

## 13. Git commit/push race and atomicity

Normal push and exact-head checks protect against a changed remote branch, not a generation change in SQLite. No B commit is needed before A becomes stale. A can publish after B is current without overwriting a newer B commit. If a newer conflicting remote commit already exists, push may fail; this narrower protection does not disprove the schedule above.

Strict no-stale-publication requires a common serialization/linearization boundary covering generation changes and Git ref publication, or equivalent enforcement by the recipient. It need not literally be a SQL distributed transaction, but independent HTTP observation plus git push is insufficient. Current workflow credentials allow push independently of the backend.

A backend publish lock would be more than a current-check contract: forbid supersession while publishing. A nonexpiring lock blocks recovery forever after worker loss; a timed lock can expire while A is paused or its push result is uncertain, restoring the same race. Crash after remote acceptance but before release introduces uncertainty. Holding a DB/network request lock or adding expiring grants without resolving that uncertainty does not establish both bounded recovery and no stale mutation. No new publish protocol is designed here.

## 14. Backend-unavailable behavior

Failure/malformed response/auth failure at a fence must fail closed: no newly authorized push and no later job reusing stale approval. This sacrifices availability; after recovery a new generation could retry. However an outage after a successful check does not revoke an already issued observation, and an uncertain in-flight push cannot be proven prevented by failing a later check. Thus fail-closed handling is necessary but does not close the core race or prove end-to-end recovery.

## 15. Recovery-threshold semantics

No X chosen. If stale work were atomically neutralized, X could affect latency, duplicate computation and cost rather than correctness. In this architecture the counterexample still exists for any X at which B may supersede A in the check-to-push interval. Avoiding overlap by choosing X above an assumed runtime returns to the lease-expiry problem, including unbounded-by-local-configuration queue delay. Supersession without proving A dead removes a liveness dependency only when stale mutation is actually prevented; that premise is not met.

## 16. Request-storm implications

SQLite can enforce one current identity, minimum supersession age, recovery budget/window and existing client/global quotas without liveness tracking. Android restarts would not reset server-owned accounting. An illustrative model bounds dispatch count to three over an hour with a synthetic budget/age; these are not recommended settings. Such bounds constrain cost and queue pressure; they do not fence any individual stale publication. Multiple queued stale runs still consume Actions capacity and may delay the useful current one. No scheduler or recovery policy implemented.

## 17. Authentication requirement

Dedicated workflow/backend secret over HTTPS, or a high-entropy per-attempt capability, could protect a strict ID/attempt current-check. Never reuse the GitHub PAT. An attempt capability would itself be credential material: prevent logs/artifacts/Android exposure and bind it to ID and purpose. A shared secret requires constant-time auth and strict size/schema/unknown-field validation. Responses must not be cached as reusable currentness grants. Old authenticated attempts must return stale; old terminal results cannot close B. Replayed positive responses or signed grants do not prove currentness at a future push. No auth, secret or endpoint was implemented/configured.

## 18. Deterministic race matrix

| Schedule | Verdict for check-only model | Reason |
| --- | --- | --- |
| A queued; B current; A starts | SAFE ONLY IF early authoritative fail-closed check | Reject A before work |
| A computing; B current; A reaches final monitored fence | SAFE ONLY IF B precedes that check | Local result can be discarded |
| A passes start fence; B current; A publishes | UNSAFE | Start admission is obsolete |
| A passes final fence; B current; A commits locally | Local commit B-class; UNSAFE if pushed afterward | Remote head can remain unchanged |
| A monitored push succeeds while current; B current; A promote starts | SAFE ONLY IF independent promote fence rejects | Existing outputs do not prove currentness |
| A promotion fence passes; B current; A production push | UNSAFE | Same TOCTOU at canonical publication |
| Old A callback after B | SAFE ONLY IF exact current-attempt match before mutation | Correlation can protect backend state |
| Backend unavailable before check | SAFE ONLY IF fail closed | No positive admission |
| Shared writer allows only A to run; backend supersedes with B | UNSAFE for A's later push | Serialization does not include backend |
| Expiring publish lock; A resumes after B supersedes | UNSAFE | Old publisher still has Git credentials |
| Nonexpiring publish lock; A disappears | Recovery blocked | No bounded release evidence |
| Repeated supersession with durable server budget | Cost bounded only | Does not close stale push |

The added 13 architecture tests explicitly interleave events. They model counterexamples/properties under stated assumptions; they do not run production git, prove a complete implementation, measure runner timing or claim provider safety. The push model intentionally uses an exact expected-head CAS, a stronger check than needed for the counterexample.

## 19. Complexity estimate

No viable LOW-complexity implementation scope is recommended. A check-only candidate would need backend current ID/time plus bounded recovery accounting (roughly three conceptual field groups; terminal state optional), authenticated checking and multi-job plumbing. That small model fails the safety property.

Closing publication ownership/uncertain completion would raise backend/workflow integration and failure recovery to **HIGH** relative to this small service. Shared Python checks could remain centralized but cannot solve remote atomicity. Provider-specific changes are not necessary or helpful. Android is outside fencing scope. These are qualitative rejected-design costs, not a proposed state machine or implementation plan.

## 22. At most three simplification directions

Ranked by simplicity first; reliability and migration effort shown independently. These are high-level alternatives only, not new recovery protocols:
