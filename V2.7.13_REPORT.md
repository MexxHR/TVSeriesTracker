## Diagnosis and confidence

**CONFIRMED from prework source:** no accepted-submission notification/follow-up existed. A request queued an asynchronous backend/workflow operation, while refresh only occurred at startup when stale or through manual Settings action. A same/older payload returned false and touched lastSyncedAt, so an early fetch could leave no follow-up and suppress another ordinary startup fetch for 24h. There was also an unprotected snapshot/compare/replace sequence permitting overlapping repository refreshes to overwrite newer data with an older result.

**STRONGLY_SUPPORTED latency contribution:** the asynchronous post-request race plus absent follow-up explains waiting despite a completed correct production promotion. It is reproducible deterministically as T1/T1 then T2 with the requested ID. This is a source/test diagnosis, not a measured attribution of every second of the user's live E2E delay.

## HTTP/cache audit and delivery strategy

Prework HttpOfficialRemoteSource constructed OkHttpClient() with no explicit Cache, interceptors, Cache-Control, ETag/If-None-Match, Last-Modified/If-Modified-Since, FORCE_CACHE or FORCE_NETWORK. A read-only local probe against the cached project OkHttp dependency confirmed default cache=null, interceptors=0 and networkInterceptors=0. Official Data does not use a configured system HTTP response cache or the Retrofit TMDB client. Room is the explicit application cache; a remote CDN may independently cache branch content, but that was not measured locally.

| Strategy | Decision |
|---|---|
| Existing canonical branch URL + bounded later GETs | Chosen; fixes the proven missing-fetch race without changing delivery architecture. The next valid NEWER payload is applied. |
| Same URL + explicit no-cache/revalidation | Not added; no local configured HTTP cache or measured CDN cause justifies a new header policy here. It cannot by itself prove that an async commit already exists. |
| Controlled query cache-buster | Not used. No timestamp/random query parameters; every attempt uses the same configured URL. |
| GitHub contents/raw API | Not needed; would add a new delivery/API dependency and quota handling without addressing the proven scheduling race. Public contents can be read without authentication, but unauthenticated API requests share an IP quota. See [GitHub contents API](https://docs.github.com/en/rest/repos/contents) and [REST rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api). |
| Commit-SHA immutable URL | Not chosen; Android does not know the newly promoted commit SHA. Learning it would require another API/backend contract or workflow awareness. [GitHub permanent links](https://docs.github.com/en/repositories/working-with-files/using-files/getting-permanent-links-to-files) identify fixed versions, not an automatic newest-data subscription. |

No GitHub authentication, Actions polling, PAT, backend endpoint, analytics service or high-frequency request loop was added. The existing manual recovery action remains available.

## Chosen bounded follow-up behavior

The actual backend QUEUED/ALREADY_QUEUED response emits the requested TMDB ID. While the UI lifecycle is active, one process-local coordinator collects accepted IDs in a set. If their verified facts already exist in the validated cache, it stops without fetching.

The shared batch allows **at most three additional refresh attempts**, with relative waits **30,000ms, 60,000ms, 120,000ms**. Nominal opportunities are about 30/90/210s after the accepted event, plus preceding request/processing time; no absolute latency guarantee is made. The waits suit the user's reported workflows completing in tens of seconds and allow additional external propagation time.

Before each wait and again immediately before a network attempt, the coordinator checks the requested IDs in cache. It refreshes only if an ID is still missing. After each attempt it checks again. A verified unrelated ID does not stop a requested ID's watcher. Late accepted IDs join the current batch's remaining budget and do not reset it. Errors consume one attempt and keep cache intact; exhausting the budget quietly clears pending IDs rather than showing a false workflow failure. The user can later refresh manually.

Stop conditions: all requested IDs found, three attempts consumed, lifecycle stop/dispose, or coroutine cancellation. A fact arriving through manual/startup refresh during a delay prevents the next unnecessary HTTP fetch. Each coroutine owns its attempt counter, so cancellation of an older batch cannot consume a restarted batch's budget.

No additional refresh WorkManager task, service or persistent job exists. Lifecycle stop cancels network/delays and drops the batch; replay=0 means no stale accepted event restarts it on resume. If processing is accepted while inactive/process-closed, normal startup/manual recovery remains available. This foreground-only tradeoff intentionally avoids continuing aggressive work when the app is closed. A new actual accepted submission may start its own bounded batch later.

## Freshness, concurrency, offline and failure safety

Production promotion already advances generatedAt for a genuine factual change and retains it for a semantic no-op. Its implementation remains byte-identical. Android continues using parsed Instant ordering:

- remote > cached: validated replacement eligible;
- remote == cached: no row replacement;
- remote < cached: stale rows rejected;
- malformed generatedAt: reject entire payload.

The repository mutex covers the fetch and comparison against a current store snapshot through replacement/touch. Two overlapping successful calls coalesce; a later independent stale response cannot overwrite a newer cache. Bootstrap participates in the same lock. Existing Room replacement is transactional. This proves the normal single-repository app path; cross-process/multiple independent repository-instance serialization is not claimed. The existing Room cache observer remains a combine of two flows and may transiently expose mixed sync/row observations; no database schema or observable redesign was introduced.

HTTP callback threads read/close the response before resuming a String; cancellation remains connected to Call while bytes are read. JSON validation runs on Dispatchers.Default. No network read, delay or JSON parse blocks the UI thread. CancellationException propagates; error messages/payloads/Authorization values are not logged.

Timeout, DNS/5xx, invalid JSON/schema/timestamp and size failures leave existing valid rows untouched. Offline startup retains bundled/Room behavior. Settings remains one logical operation with its existing loading/result UX. Startup remains one staleness-gated fetch and the 24h interval is unchanged. No periodic frequency was increased.

Debug diagnostics are bounded local logs only: refresh reason, attempt and requested IDs, cached/remote generatedAt, NEWER/SAME/OLDER/COALESCED decision, elapsed milliseconds and failure class. No secret, full JSON or private payload is logged. These logs support the future manual T0/T1/T2 measurement; no telemetry backend was introduced.
