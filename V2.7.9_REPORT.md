## Root blocker and discovery architecture

The baseline demonstrates parser/replay compatibility but no generic discovery passes and insufficient distinct-series coverage. V2.7.9 addresses discovery plus corpus breadth, rather than rewriting the Spanish parser or weakening qualification.

New module `hbo_max_discovery.py` receives only an HTTP getter and title aliases. It has no oracle/known-article argument. Runtime starts from these generic entry points:

- `https://press-spain.max.com/`
- `https://press-spain.max.com/sitemap`
- `https://press-spain.max.com/post`

Pipeline: fetch first-party index -> extract observed anchors or XML locs -> canonicalize -> deduplicate -> bounded traversal -> exact title relevance -> lifecycle/brand relevance ranking -> concrete article fetch -> existing identity and provider validation -> parser -> bounded evidence -> fresh independent reconstruction.

Discovery now uses its own structural-link extractor. It includes nav/footer index links, which may be discovery surfaces, while ignoring scripts/styles. This does not alter article editorial extraction or factual trust. It preserves safe listing query parameters so different pagination/search URLs remain distinct, while removing article query/fragment/trailing-slash variants for deduplication. Redirecting an index directly into an article does not establish discovery proof. HTTPS, exact hostname, default/443 port, no userinfo and safe path/query validation remain mandatory. External links and arbitrary endpoints are rejected.

Candidate ranking is deterministic: generic lifecycle wording first, matching route-brand wording second, then canonical URL. Ranking never verifies provider identity. It does not inspect oracle URLs or expected status/season values. Title normalization handles case, Unicode punctuation, HTML entities, curly apostrophes and conventional slug apostrophe omission, retaining accents and whole token boundaries. It performs no fuzzy edits or invented translations.

Bounded XML urlset/sitemapindex parsing is also supported if such a child is actually linked. Lastmod is diagnostic only. DOCTYPE/entity-bearing XML is rejected. XML support is fixture-tested, not claimed as an observed live source structure.

Following observed links produced public listing URLs with `limit=30`, then `limit=45`, `offset=0`, `searchKey=` and `tab=all`. The crawler follows only observed, validated pagination links; it does not invent arbitrary archive offsets. Script/lazy-load execution, private APIs and cookie/auth mechanisms are not used.

After a current first-party page exposes that public `/post?...searchKey=...` GET template, runtime may construct bounded title-only search queries from it, resetting offset to zero and retaining its other allowed parameters. There is no speculative search endpoint when the template is absent. Nonempty searchKey development web requests returned tool Internal Error, so successful filtering is not claimed locally. A runner must actually fetch the index and independently discover/validate articles; an ignored/failed search cannot fabricate a pass. The response is treated as HTML discovery only.
