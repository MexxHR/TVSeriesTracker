## 8. Smallest required backend contract change — proposal only

Required behavioral delta: distinguish **a useful active processing attempt** from **a historical dispatch acknowledgement**, and allow one atomically reserved, bounded recovery attempt when the prior attempt is confirmed retryable/terminal or its server lease can safely expire without leaving active duplicate work.

Keep the normal ID-only Android request and existing queued/already_queued compatibility; Android must not track GitHub internals. Backend owns per-ID recovery eligibility, minimum spacing and retry budget. A server-provided next eligible retry time can prevent client storms, but adding that response field alone does not remove the24h blocker.

Safe active-attempt correlation needs trusted server/workflow evidence or an explicitly designed lease/completion signal. Current204 acknowledgement supplies no stored run correlation. If a minimal authenticated workflow completion/lease signal is required, that is an additional runtime workflow change requiring explicit scope approval; no such change is made here. The precise correlation mechanism must be reviewed before implementation. **Do not simply shorten COOLDOWN_SECONDS or add an unrestricted client forceRetry flag.**

Duplicate-dispatch implications: preserve atomic per-ID reservation/BEGIN IMMEDIATE, deny recovery while useful work is active, handle concurrent clients idempotently, and retain workflow shared-writer/canonical idempotency guards. An expiry-only shortcut can queue duplicate active runs, so that tradeoff must not be hidden.

Rate-limit implications: keep per-client/global charging and quotas; charge authorized recovery attempts; bound per-ID retry rate and total attempts; provide deterministic retry timing without allowing restart/reconciliation loops to increase dispatch volume. Credentials and any trusted completion signal remain server-side and out of Android/logs/archives.

Approval would authorize designing/testing this narrow recovery contract, not provider/backend queue rearchitecture or automatic production deployment. If preserving the backend freeze instead is required, an Android-only foundation can be scoped explicitly to late-publication recovery and eventual >24h redispatch, but must not be presented as satisfying every minutes-level failure scenario.
