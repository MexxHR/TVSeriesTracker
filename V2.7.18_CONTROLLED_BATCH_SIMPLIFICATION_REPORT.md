# V2.7.18 — Controlled Batch Simplification Design

**V2.7.18 CONTROLLED BATCH — CONTROLLED_BATCH_RECOMMENDED_WITH_CONDITIONS**

**GO_CONTROLLED_BATCH — design/planning only.** Date: 2026-10-16, Europe/Zagreb. Runtime is frozen at versionCode48 / versionName2.7.16.1 / Room3 / applicationId com.example.tvseriestracker. No implementation, live request, dispatch, provider fetch, deployment, APK or release ZIP.

## 1. Executive verdict

A durable pending set plus serialized, at-least-once batch processing materially simplifies server recovery. Failed or absent work leaves the row pending; a later scheduled run retries it. No server decision about GitHub liveness, obsolete publishers or lease expiry is necessary. A newer submission does not revoke an older batch's publication rights: it only prevents that batch's ACK from consuming the newer request. This deliberately removes the strict supersession/publication relationship that caused the fencing blocker.

Conditions for implementation planning:

1. ACK only a verified per-ID processing outcome after required remote publication, or a validated terminal no-fact pass. Never ACK mere local writes, regression success, monitored-only VERIFIED_FACTS or an uncertain push.
2. Use a small request receipt and atomic conditional ACK; retain bounded completion evidence for Android. A missing row alone does not prove completion.
3. Whole-batch writer serialization, bounded fair selection and safe error isolation must preserve existing validation/global failure rules. No continue-on-error over an unsafe checkout.
4. Close the actual long-term monitoring gap: current daily automation processes trusted sources only. Reuse the monitored registry for a separate low-frequency selection path; do not claim it already refreshes arbitrary added series.
5. Accept best-effort minutes latency, not a cron deadline. Independently validate scheduler behavior, runner budget and tiny home-app volume before activation. Backend and GitHub outages can delay completion indefinitely without losing pending membership.

These are local queue/completion and integration conditions, not a distributed attempt-recovery protocol. The report supports implementation planning, not production readiness or a measured live KPI.

## 2. Why request-driven recovery was rejected

The three previous reports remain source of truth. Current acknowledgement history suppresses retries for24h even after failed work. A terminal callback/TTL cannot distinguish lost work from healthy queued/running work. A current-generation check cannot atomically revoke a GitHub push after a positive response. Android persistence alone cannot fix those server constraints.

Batch does not try to improve those mechanisms. It removes immediate per-ID dispatch from submission and never supersedes a workflow's publication authority. Repeating a serialized legitimate processing pass is allowed. Only backend request membership/completion is conditionally consumed.

## 3. Current architecture

Android trackAndQueueMonitoring inserts into local repository/Room, then best-effort enqueues WorkManager, swallowing enqueue exceptions. Unique official-monitoring-ID work uses KEEP, connected-network constraint,30-second exponential backoff and bounded temporary retries. It POSTs only tmdbId. A202 queued/already_queued completes the worker and emits a process-local SharedFlow event.

App validates exact bounded JSON and charges client/global quotas. RequestStore.submit serializes SQLite, applies24h dedup, dispatches GitHub with PAT and writes acknowledgement timestamp. process-series-request.yml holds official-data-writes across monitored_update and conditional promote. It validates/tests, checks exact main, snapshots protected files, processes monitored evidence, verifies allowed changes, pushes monitored registry/audit, then independently validates/reconstructs/promotes and pushes canonical/audit. Promotion requires the exact kill switch and VERIFIED_FACTS; NO_CHANGE does not publish.

RequestedOfficialRefresh runs foreground-only T+30/90/210 follow-ups, clears pending on stop/budget exhaustion and discards any cached ID. OfficialDataRepository supplies validated HTTPS fetch, Instant ordering, mutex/coalescing and canonical Room cache; ordinary startup is stale-after24h. This cannot reliably reconcile a delayed batch.

## 4. Proposed batch architecture

```text
Add -> local watchlist + durable local awaiting-submission intent
    -> ID-only POST -> SQLite pending membership + receipt -> 202
Scheduled batch -> authenticated bounded snapshot of due pending IDs
    -> existing per-ID monitored processing + independent promotion guards
    -> required git pushes / validated terminal pass
    -> authenticated conditional ACK of snapshot receipt
Android foreground/resume -> receipt status + shared canonical refresh
    -> resolve immediate processing obligation; display only canonical facts
```

Keep membership until ACK. No destructive dequeue, running state, workflow IDs, claims, leases, heartbeat, liveness polling or publisher generations. GitHub remains the serialized publication owner. A scheduled trigger is not created in this task.

## 6. Backend pending-set model

Recommended single small request table, one row per ID, with five conceptual fields:

| Field | Need |
| --- | --- |
| tmdb_id PRIMARY KEY | Set membership/dedup |
| request_receipt | Unique per accepted POST; exact ACK/status correlation, including equal clock timestamps |
| requested_at | Original enqueue time for pending request ordering and operations |
| next_eligible_at | Fair bounded retry selection; prevents poison head-of-line starvation and repeated hot retries |
| completed_at nullable | Bounded completion receipt for Android; pending means NULL |

No per-workflow attempt ID/count/status history. Rows with completed_at=NULL are the pending set; completion changes membership logically without immediately destroying evidence. tmdbId+requestedAt alone is enough only for a weaker coalescing contract without ACK-race/completion/fairness requirements. Clock timestamps are not reliable unique versions.

On repeated POST while pending, keep original requested_at and retry eligibility, replace receipt and keep pending. This is idempotent in membership, not byte-identical metadata. ID-only clients cannot distinguish a lost-response retry from a genuinely new request; conservatively treat every accepted POST as newer intent. Marker churn can defer ACK under constant submissions, but existing quotas bound it and normal clients stop POSTing after202. Do not reset poison backoff on each duplicate.

Selection orders next_eligible_at, requested_at, tmdb_id and selects at most3 due IDs. Atomically move selected next_eligible_at forward by one schedule interval. This scheduling touch is not a claim: rows remain pending, no ownership/exclusive processing right is recorded, and nothing needs release after a crash. Next eligible time can be conservatively deferred after an understood failure using the same receipt comparison. No attempt counter needed for a fixed retry delay. Retain completion records for an initial design window of7days, then discard on ordinary endpoint housekeeping; expired/absent status is UNKNOWN, never assumed complete. No daemon cleanup required.

## 7. Request endpoint semantics

Keep POST /v1/series-requests with exact {tmdbId} body, existing limits and202 accepted=true, tmdbId, queued/already_queued. Add optional requestReceipt response metadata for new Android. Existing classifier reads only state and remains wire-compatible. SQLite commit must precede202. DB failure returns retryable failure; no GitHub request in this path. GitHub outage cannot prevent queue insertion.

Costs: processing waits for batch, backend now retains unfinished intent, and old clients still lack reliable long-lived reconciliation. Public anonymous POST remains abuse-limited and must have a bounded total pending capacity with explicit retry response, never silent eviction. At home scale an initial1000-row ceiling is ample but must be tested; it is not permission to support internet-scale traffic.

## 8. Batch fetch mechanism

Prefer a dedicated authenticated bounded **POST /internal/series-batch/snapshot**, rather than a GET with mutation side effects or a formal claim. Strict empty/small request schema, server-owned max3, bounded body/response and IDs/receipts only. Do not expose the queue publicly. Returning IDs does not confer verified facts.

Each returned item carries a backend-issued ACK proof bound to purpose+ID+receipt. A domain-separated HMAC can provide proof of inclusion without persisting batch/run history. Only the snapshot endpoint issues it. ACK requires dedicated batch authentication AND valid proof/current receipt. This rejects unselected IDs and stale rows. New-request receipts are not publication fencing tokens.

Authenticated GET with pure read snapshot is smaller if fairness is otherwise solved, but oldest-only selection can starve behind poison items. Claim endpoint requires ownership/release/expiry and is rejected. No existing suitable authenticated queue API exists; current backend config authenticates outbound GitHub/TMDB, not inbound batch access. No public list, Android secret or workflow dispatch fallback.

## 9. Snapshot vs claim decision

Choose SNAPSHOT. Work stays pending through local compute, monitored push, promotion and final ACK. At-least-once processing is explicit. Crash anywhere before ACK is naturally retryable. Snapshot selection metadata affects when an item is retried, not whether it exists or whether an old worker may publish. Empty snapshots exit without provider calls. Regression gates must still run before any processing publication; skipping gates merely because a nonempty batch is small is prohibited.

## 10. Batch concurrency

Use the existing workflow-level official-data-writes group with cancellation disabled for the entire processing/publication unit. A batch-only dedicated group would not protect against daily/manual writers. Do not split jobs into independent per-ID workflow dispatches. Sequential per-ID units within one batch can reuse current monitored->promote checks; a bounded matrix is possible only if its publication is also serialized and failure semantics proved, so prefer sequential.

Scheduled runs may queue; delayed runs fetch their snapshot when admitted, not before waiting. Redundant queued runs often find no work. Even if one run is canceled/dropped before admission, DB intent remains. The design depends on writer serialization, not backend claims. External manual pushes remain subject to existing exact-head/normal push failure; pending survives failure. Actions concurrency behavior must be confirmed for deployment; no live scheduler guarantee is claimed here.

## 11. Recommended frequency

Recommend a requested **10-minute interval**, offset from the hour boundary (illustrative minutes3,13,23,33,43,53). Five minutes doubles empty-run overhead/provider retry opportunities and still cannot promise starts. Fifteen minutes lowers overhead but adds five minutes to worst nominal wait and failed-run recovery. Ten balances tiny home volume and reasonable minutes UX. Maximum3 selected IDs/run, no provider work when empty, fixed transient deferral of one or a few intervals rather than high-frequency loops.

Requested nominal runs/day:5min=288;10min=144;15min=96. These are arithmetic, not executed-run counts or provider-call counts. Runner budget/availability/private-repo billing and current GitHub scheduling rules must be checked before activation; no remote checks were performed under no-live scope. Cron interval is not an execution deadline. Shared queue wait, provisioning, dropped triggers and outage can exceed it without creating a safety race.

## 12. Per-ID outcome matrix

ACK means the immediate processing pass is terminally understood, not that a future-season fact exists.

| Outcome | ACK/remove pending? | Retry / terminal rule |
| --- | --- | --- |
| Valid canonical factual change successfully pushed | YES | Complete pass; no more immediate retry |
| Independently validated canonical NO_CHANGE | YES | Complete pass with existing canonical unchanged; require successful monitored push if changed |
| VERIFIED_FACTS staging only, promotion not completed or disabled | NO | Keep/defer; kill switch is respected, configuration may require manual action |
| Clean NO_VERIFIED_FACTS | YES after permitted staging publication | No verified fact found in this pass; never assert factual absence |
| Clean NOT_PARSER_ELIGIBLE / DISCOVERY_INSUFFICIENT | YES only if bounded processing completed without access/transport errors | Terminal immediate insufficient-evidence pass; no trust upgrade |
| Clean UNSUPPORTED_PROVIDER/unknown network | YES after valid outcome/staging guard | Terminal immediate request, no endless frequent retry; no inferred provider |
| PROVIDER_UNAVAILABLE / METADATA_UNAVAILABLE / transient HTTP | NO | Keep, defer, preserve exact prior verified record and lastChecked |
| Regression gate / infrastructure failure | NO | No success inference; next batch retains work |
| Git conflict / push failure / uncertain push acceptance | NO | Next clean batch validates/reprocesses; no rebase/force push shortcut |
| Malformed POST | Never admitted | Return existing4xx; not a poison queue row |
| Conflicting evidence / VALIDATION_FAILED / corrupt/global safety state | NO | Preserve publish-blocking behavior; defer offending selection, truthful failure, operator inspection if persistent |
| Unexpected exception | NO | Fail the unsafe unit/run; no silent per-item success or ACK |
| ALREADY_TRUSTED | NOT automatically complete | See trusted-path condition below |

**Trusted path gap:** monitored.process deliberately returns ALREADY_TRUSTED without fetching evidence for sources.json IDs. That is not a completed fresh processing pass. A batch adapter must route those IDs through the existing trusted collect/merge/validate/publish path, ideally a narrowly parameterized trusted run selection retaining complete-dataset/global guards. Do not duplicate provider logic or run all12 trusted providers every10minutes merely for one ID. If this integration is deferred, disclose trusted-ID immediate processing as unsupported by the new KPI; do not ACK it as freshly checked.

## 13. NO_CHANGE semantics

Current promotion.promote independently validates persisted evidence and returns NO_CHANGE before update.publish when facts are already represented. Replayed successful publication can therefore conclude cleanly without advancing generatedAt or appending production audit. Normal new evidence may legitimately produce a later factual change; at-least-once is not a guarantee of byte equality under changing real evidence.

ACK may record completed_at for the receipt without a provider status enum. Android can then know its processing pass finished even when canonical generatedAt is unchanged. Completion does not mean the canonical endpoint has already delivered the newest bytes through all caches, nor does it supply new facts. Receipt status and canonical refresh are separate.

## 14. No-evidence semantics

After one successful, bounded, validated pass with no usable facts, finish the immediate request rather than retrying every10minutes forever. Show the existing canonical fact if any, otherwise existing unknown/no-verified-data UI. Do not call this proof that no official announcement exists. Access failures and incomplete/failed metadata do not qualify as successful no-evidence passes. Preserve existing provider safety semantics.

Long-term discovery uses the monitored registry at low frequency, not a permanent high-frequency pending row. Current implementation does not yet schedule that registry; section25 makes this an explicit integration condition.

## 15. Transient failure semantics

Leave pending and wait for a later admitted batch. A one-interval selection deferral is enough for ordinary single-run failure. Repeated known provider/network failures can use a simple fixed longer next_eligible_at, for example30minutes, with bounded diagnostic counts; no per-run lease or exponential attempt state needed. Persistent configuration/validation errors may need operator action and must not be disguised as automatic eventual success. No maximum successful recovery time can be promised during outages.

## 16. Poison-item handling

Reject malformed IDs before insertion. Select at most3, rotate via next_eligible_at and use deterministic ordering. Failed selections do not remain permanently at the head; even if a run aborts on ID1, unselected IDs with earlier eligibility can be chosen next time. The model explicitly checks this case.

Per-ID units must begin from a clean validated repository boundary. Continue after understood per-ID unavailable/nonfatal outcomes only when existing safety rules permit it. Conflicts, corrupt audit/schema, unexpected exceptions and unsafe checkout remain publish-blocking for the affected unit/run. Do not wrap them in generic continue-on-error or reuse dirty local files. Independent future clean batches and fair selection, not weakened validation, prevent one ID blocking unrelated work indefinitely. A global corrupt repository cannot be safely bypassed and requires repair.

## 17. ACK contract

Conceptual authenticated POST /internal/series-batch/complete, per-ID or bounded list of at most3. Require exact ID/receipt/proof schema, strict types/lengths/content size, duplicate-key/unknown-field rejection and constant-time auth/proof validation. Do not accept provider facts as ACK authorization.

In one SQLite transaction: verify snapshot proof and current receipt; if pending, set completed_at; if already completed for that receipt, return idempotent already_complete; if current receipt differs, stale/no mutation. Do not delete a newer row or mark it complete. A batch cannot ACK an ID outside its issued snapshot proof. Trusted workflow code must additionally enforce outcome/push ordering; authentication cannot independently prove provider processing happened. No run tracker/history table is needed.

## 18. New-request-before-old-ACK race

```text
T0 POST123 -> row receipt R1, pending
T1 snapshot -> (123,R1,proof1)
T2 new POST123 -> same membership, receipt R2, pending
T3 old batch may legitimately publish its valid result
T4 ACK(123,R1,proof1) -> stale; R2 remains pending
T5 later batch processes R2 and ACKs it
```

Exact receipt matching is atomic entirely within SQLite. No git transaction or publication revocation is involved. Same timestamp submissions receive distinct receipts. If ACK linearizes first, the later POST inserts a fresh pending obligation; either ordering is safe. Completed row expiry must never reuse a receipt. Marker is request correlation only, not an attempt/generation fencing protocol.

## 19. Publication-before-ACK replay

Remote push succeeds, ACK fails: row remains pending. Next serialized batch checks out current main and redoes the same guarded pipeline. Existing canonical facts remain; identical facts yield NO_CHANGE, unchanged monitored rows suppress lastChecked-only churn, and new valid evidence is handled by normal merge/conflict rules. ACK can then complete the request. Duplicate ACK is idempotent. No rollback of successful canonical publication merely to match DB membership.

An uncertain push is treated as unacknowledged. Subsequent clean checkout determines repository state through the ordinary pipeline, not backend polling. Tests below include existing promotion tests plus a toy replay model; no real runner replay was executed.

## 20. Scheduled batch failure / queue delay

Never-started, dropped, queued or failed-before-snapshot run changes no membership. Crash after snapshot changes only next eligibility; pending remains. Failure before publication means no ACK. Another scheduled opportunity retries; backend never asks whether the previous run lives. Duplicate serialized batches may repeat computation but do not grant new publication authority or invalidate an earlier publisher.

Delayed triggers add latency, not a backend supersession race. If scheduling remains disabled indefinitely, pending is durable but never progresses: manual operational correction is required. This limitation is explicit and materially simpler than tracking individual run state.

## 21. Existing provider pipeline reuse

Reuse registry, routing, discovery, fetched identity/evidence checks, parsing, reconstruction and monitored.process. No provider adapter changes, inferred TMDB facts, alternate allowlists or bypasses. A batch orchestration layer interprets existing pipelineState and guarded results. It must distinguish unavailable from clean insufficient evidence, including preserved MAX evidence returned with PROVIDER_UNAVAILABLE. Existing verified bytes/lastChecked remain protected on unavailability.

## 22. Existing promotion reuse

Reuse automatic_promotion snapshot/verify-stage, manual_promotion_guard preflight/verify-auto, promotion.promote and update.publish. Preserve promotion kill switch, exact main/head boundaries, one-ID changes, two monitored/two production file allowlists, independent replay, conflict handling and truthful failures. Process IDs sequentially with fresh clean boundaries after each push; do not validate a multi-ID accumulated dirty tree with a one-ID guard.

Keep the original daily maximum-four factual-change guard. Initial request batch cap3 also bounds distinct request-driven factual changes below4; if future low-frequency processing shares the run, enforce a combined maximum4 and defer remaining changes. Do not silently weaken global guards by treating N separate calls as unlimited publication permission.

## 23. Android simplification

KEEP local watchlist/Room, unique connected WorkManager transport, strict response compatibility and OfficialDataRepository/cache. MODIFY Add handling to durably record awaiting-submission/result intent independently of enqueue success; persist the optional receipt after202. Repair missing/terminal submission work on foreground/resume/startup with bounded backoff and existing quotas. Do not repeatedly POST after acceptance merely to check progress.

REPLACE finite accepted-event polling as correctness mechanism with one lifecycle-aware reconciler over durable unresolved IDs. A process-local event may wake it but cannot own state. Initial concept: refresh/status on startup/resume, then at a modest2-minute foreground cadence while unresolved, coalescing all IDs and backing off failures. Pause network work in background; keep intent. No permanent service/Firebase/GitHub polling. Ordinary24h startup behavior stays for users without unresolved intent. No implementation or cadence guarantee here.

## 24. Android completion criterion

Pending disappearance alone is insufficient: it could mean never submitted, purged, restored DB, expired receipt or another request replaced it. Prefer a minimal receipt status endpoint (bounded POST body rather than sensitive query URLs) returning pending, complete or unknown/superseded for the exact ID/receipt. It exposes neither pending list nor provider facts. These are query results derived from receipt/completed_at, not stored workflow states or a permanent outcome history.

On matching complete, immediate Add-triggered processing is done, including NO_CHANGE/no-fact pass. Android must still perform a successful shared canonical reconciliation; on network failure retain local fetch obligation. SAME can be a successful fetch and must not replace newer cache. Receipt completion alone must never create a factual status. CDN/read visibility after ACK may need a bounded follow-up; no strict latest-content guarantee can be inferred from membership or a global timestamp. If exact publication-content visibility must be proven, a per-receipt expected content identity would be an additional reviewed requirement, not silently added here.

**ANDROID_COMPLETION_CRITERION_PENDING** is narrowed by the receipt/pass contract but not declared implemented or fully closed. Expired/unknown receipts cause bounded resubmission/reconciliation rather than false completion. Multi-client supersession requires handling unknown/superseded, not clearing someone else's obligation. At tiny home scale this remains small; no accounts/device IDs added.

## 25. Future long-term monitoring separation

Actual daily schedule: update-official-data.yml at07:17UTC invokes update.run, which iterates registry['series'] from sources.json. It does not iterate monitored_series.json or arbitrary watchlist/added IDs. sources registry validation currently expects12 trusted entries. Supplemental canonical entries are preserved/validated, not freshly discovered by that loop. Android Room watchlist is not available to GitHub.

Therefore removing a clean no-evidence request from high-frequency pending MUST NOT be described as handing it to existing automatic global monitoring. Proposed minimal integration: a separate low-frequency selection over the existing monitored registry, reusing the same per-ID processing/promotion and shared writer group, while preserving trusted precedence and exact safety guards. No new permanent backend watch queue or auto-add to sources.json. Bound/fairly rotate at home scale and respect maximum-four factual changes. Unsupported providers remain inactive/terminal until an explicit supported route exists. Validate this integration before claiming future-announcement coverage; it is a real required change, not present behavior.

## 26. Latency model

Illustrative assumptions, not measurements: interval I=10min, admitted processing+publication P=1–4min, foreground reconciliation wait C=0–2min; no backlog/outage. Total = wait-to-trigger + queue/provisioning delay D + P + C.

| Case | Conceptual visible-result latency with D=0 |
| --- | --- |
| Just before batch snapshot | About1–6min |
| Mid-interval | About6–11min |
| Just after snapshot | About11–16min |
| One failed scheduled opportunity | Add about10min plus any failed-run occupancy/backoff |
| GitHub/shared writer delay | Add actual D; no finite guaranteed upper bound |
| App backgrounded | Automatic on next active reconciliation; not a background-display SLA |

These examples reasonably fit a home-app minutes expectation only if real admitted runtime/load is similar. Existing provider budgets/regression/setup can exceed assumed P; measure separately after implementation approval. Reliable eventual processing requires future scheduled opportunities and reachable dependencies, not exact cron timing.

## 28. Concepts removed vs added

Actual removals after safe migration: synchronous GitHub API dependency/retry error mapping in submission; outbound dispatch credential path;24h dispatch-history gate; per-Add workflow trigger fan-out; process-local accepted event as correctness owner; finite three-refresh pending clearing. Proposed but unimplemented lease/attempt/liveness/fencing designs become unnecessary, not counted as deleted code.

Added server concepts: pending membership, conditional receipt completion, bounded fair selection. Added client concept: durable unresolved intent/reconciliation (already needed for the original KPI). Low-frequency monitored selection is an existing product gap, independent of immediate retry. More fields/endpoints than today's broken acknowledgement table are required; the compelling reduction is eliminating cross-system run recovery and moving retry correctness to durable membership. No claim that total lines must shrink, and no claim future monitoring comes free.

## 29. Security / credential model

Android keeps no GitHub/PAT/batch secret. It holds its own opaque request receipt only for correlation/status; do not log it or use it to authorize publication. Backend keeps durable DB, CLIENT_IP_HMAC_KEY, TMDB proxy credential and trusted proxy configuration. For this path TARGET_REPOSITORY/GITHUB_REF/backend GitHub PAT become unnecessary after old dispatch is retired; assess any other deployment use before removing them. GitHub's workflow GITHUB_TOKEN remains for existing contents writes.

Proposed dedicated SERIES_BATCH_API_SECRET configured only in GitHub Actions secrets and PythonAnywhere environment; never reuse PAT. It authenticates snapshot/ACK; domain-separated HMAC can also bind ACK proof. Strict HTTPS endpoint/redirect policy prevents secret leakage. Constant-time comparisons, schema/body limits, bounded lists and anti-replay receipt matching are required. Public status must be exact-receipt, nonenumerable and quota-limited; no public pending list/raw IP/device history. Response no-store, sanitized summaries, no secret-bearing curl command output. No credential created/changed here.

Minimal summary: fetched, processed, completed, retained, failed, no-change, oldest due age. Keep counts and coarse reasons, not payloads/receipts/secrets. Pending backlog is an operational warning, not proof of current run liveness. Scheduler/API limits/budget require separate preactivation verification.

## 30. Deployment sequence

Stage additive DB schema/API support first while old submission mode stays active. Back up durable DB; preserve legacy requests/rate events and existing client response contract. Legacy24h rows prove dispatch only: import them conservatively as pending when switching modes, paced/fairly selected rather than assuming completed. Do not destroy tables or reset quotas.

Install batch workflow/orchestrator and secret configuration in paused/readiness mode. Only after it can fetch/validate and is ready to process, atomically switch submission to pending-set semantics. Drain or retire old immediate dispatcher triggers; queued old runs remain legitimate guarded writers under shared group. Capture outstanding legacy IDs so the transition cannot lose accepted work. Do not dual-dispatch new Adds as the steady state.

Verify end-to-end batch behavior under separately authorized controlled acceptance, then roll out Android receipt/durable reconciliation. Old Android clients can submit unchanged but retain old automatic-refresh limitations until upgraded. Do not promise full phone KPI after backend-only cutover. Activate low-frequency monitored refresh before claiming future announcements, then retire obsolete credential/code only after review. No deployment executed now.

## 31. Rollback

Pause batch processing, retain all pending/completion rows and rate state, and restore prior endpoint mode if necessary. A simple old-mode switch alone will NOT drain IDs accepted only into the new set; preserve and explicitly reconcile/drain that backlog using a controlled authorized path before declaring rollback complete. Never reinterpret pending receipts as successful dispatch timestamps or delete them to fit the old schema.

Additive schema lets the prior service coexist without a destructive migration rollback. New Android must tolerate old response without receipt and retain its local unresolved intent. Existing canonical commits stay unless a separate validated data rollback is authorized; do not roll them back to synchronize queue state. No automated rollback protocol designed or run.
